# Database and cloud

Cloud provider: **Cloudflare** (confirmed). Reuse the technologies and patterns here. Create **new** resources for the new app; never point it at the source app's database, bucket, Worker, domain, or credentials.

## 1. Services and their roles

| Service | Binding / name in config | Purpose | Needed in new app? |
| --- | --- | --- | --- |
| Cloudflare D1 (SQLite) | binding `DB` | All relational data, including Better Auth tables (users, sessions, OAuth clients, tokens, JWKS) | **Yes** |
| SQLite FTS5 (inside D1) | virtual table + triggers | Full-text search | Only if you need search |
| Cloudflare R2 | binding `MEDIA` | User-uploaded files | Only if you store files |
| Worker secrets | `wrangler secret put` | API keys and auth secrets | **Yes** |
| Worker vars | `vars` in `wrangler.jsonc` | Non-secret config (`PUBLIC_BASE_URL`) | **Yes** |
| D1 Time Travel | built into D1 | Point-in-time restore (7 days on free plan, per source docs) | Use it |

Not used (confirmed absent): KV, Durable Objects, Queues, Hyperdrive, Cache API, cron triggers, any external Postgres/MySQL.

## 2. Database client and connection management

- **Workers**: `drizzle(env.DB, { schema })` from `drizzle-orm/d1`, built **per request** in `worker.ts`. No pool; the D1 binding is the connection.
- **Node host / tests**: `better-sqlite3` file or `:memory:` + `drizzle-orm/better-sqlite3`; `PRAGMA journal_mode = WAL` and `PRAGMA foreign_keys = ON` on the Node host; migrations applied at startup with `migrate(db, { migrationsFolder })`.
- **One type for both**:

```ts
// server/adapters/db.ts
import type { BaseSQLiteDatabase } from "drizzle-orm/sqlite-core";
import type * as schema from "../db/schema";
// eslint-disable-next-line @typescript-eslint/no-explicit-any
export type Database = BaseSQLiteDatabase<"sync" | "async", any, typeof schema>;
```

Rule: **always `await` queries** (works on both the async D1 and the sync driver).

## 3. Transactions: `atomic()`

D1 has no interactive transactions; it runs a `batch` as one transaction. better-sqlite3 has sync transactions. One helper covers both:

```ts
// server/adapters/atomic.ts
export async function atomic(db: Database, statements: Array<() => unknown>): Promise<unknown[]> {
  const anyDb = db as any;
  if (typeof anyDb.batch === "function") return anyDb.batch(statements.map((build) => build()));
  const results: unknown[] = [];
  anyDb.transaction(() => {
    for (const build of statements) {
      const query = build() as { run?: () => unknown } | undefined;
      results.push(typeof query?.run === "function" ? query.run() : query);
    }
  });
  return results;
}

/** Affected rows: D1 `{ meta: { changes } }` or better-sqlite3 `{ changes }`. */
export function changesOf(result: unknown): number {
  const v = result as { changes?: number; meta?: { changes?: number } } | undefined;
  return v?.meta?.changes ?? v?.changes ?? 0;
}
```

Constraint: statements in one `atomic()` call cannot read each other's results. Read first, then write in one batch; use conditional `WHERE` clauses (e.g. `where revision = expected`) plus `changesOf()` for optimistic concurrency.

## 4. Schema conventions

```ts
// server/db/app-schema.ts (generic example)
import { sql } from "drizzle-orm";
import { index, integer, sqliteTable, text, uniqueIndex } from "drizzle-orm/sqlite-core";

export const items = sqliteTable(
  "items",
  {
    id: text("id").primaryKey(),                                   // crypto.randomUUID()
    title: text("title").notNull(),
    notes: text("notes"),
    tags: text("tags", { mode: "json" }).$type<string[]>().notNull().default(sql`'[]'`),
    revision: integer("revision").notNull().default(1),            // optimistic concurrency
    createdAt: integer("created_at", { mode: "timestamp_ms" }).notNull(),
    updatedAt: integer("updated_at", { mode: "timestamp_ms" }).notNull(),
    createdBy: text("created_by"),
    updatedBy: text("updated_by"),
    deletedAt: integer("deleted_at", { mode: "timestamp_ms" }),     // soft delete
  },
  (t) => [index("items_updated_idx").on(t.deletedAt, t.updatedAt)],
);

export const settings = sqliteTable("settings", {
  key: text("key").primaryKey(),
  value: text("value").notNull(),
  updatedAt: integer("updated_at", { mode: "timestamp_ms" }).notNull(),
  updatedBy: text("updated_by"),
});
```

```ts
// server/db/schema.ts
export * from "./auth-schema";   // generated by the Better Auth CLI
export * from "./app-schema";
```

Conventions observed in the source:

- Text primary keys from `crypto.randomUUID()` (injected as `newId()` into core for testability).
- Time as `integer` `timestamp_ms`; `now()` injected into core.
- JSON columns via `text(..., { mode: "json" }).$type<T>()`.
- Enums via `text(..., { enum: [...] })` (not enforced by SQLite; validate in core).
- Case-insensitive unique names: `uniqueIndex(...).on(sql\`${t.name} collate nocase\`)`.
- Idempotency: `uniqueIndex` on `(credential_id, idempotency_key)`.
- Soft delete with `deleted_at`; queries filter `isNull(deletedAt)`.
- Revision history as a separate table of JSON snapshots (business feature; optional).

## 5. Migrations

- `drizzle.config.ts`: `{ dialect: "sqlite", schema: "./server/db/schema.ts", out: "./db/migrations" }`.
- Generate after schema changes: `npm run db:generate` (`drizzle-kit generate`). Commit the `.sql` file **and** `db/migrations/meta/`.
- Apply on Cloudflare with Wrangler (the `migrations_dir` in `wrangler.jsonc` points at `../../db/migrations`, relative to the config file). Wrangler records applied files in a `d1_migrations` table.
- Apply on Node/tests with Drizzle's `migrate()` reading the same folder.
- **Custom SQL** (FTS5 virtual tables, triggers, data backfills) goes in its own migration file, separated with `--> statement-breakpoint` lines like generated files. (Inferred: created with `drizzle-kit generate --custom`; the command is not in the repo.)
- Rules from the source's agent guide: never edit an applied migration; add a new one. Apply all pending migrations with one command, in order. Migrations should only add tables/columns/indexes so the running version keeps working during deploys.

Optional FTS5 pattern (confirmed in source; generic names):

```sql
CREATE VIRTUAL TABLE `items_fts` USING fts5(`item_id` UNINDEXED, `title`, `notes`, tokenize = 'unicode61 remove_diacritics 2', prefix = '2 3');
--> statement-breakpoint
CREATE TRIGGER `items_fts_insert` AFTER INSERT ON `items` BEGIN
  INSERT INTO `items_fts` (`item_id`, `title`, `notes`) VALUES (new.`id`, new.`title`, coalesce(new.`notes`, ''));
END;
--> statement-breakpoint
CREATE TRIGGER `items_fts_update` AFTER UPDATE ON `items` BEGIN
  DELETE FROM `items_fts` WHERE `item_id` = old.`id`;
  INSERT INTO `items_fts` (`item_id`, `title`, `notes`) VALUES (new.`id`, new.`title`, coalesce(new.`notes`, ''));
END;
--> statement-breakpoint
CREATE TRIGGER `items_fts_delete` AFTER DELETE ON `items` BEGIN
  DELETE FROM `items_fts` WHERE `item_id` = old.`id`;
END;
```

Query: ``sql`${items.id} in (select item_id from items_fts where items_fts match ${matchExpression})` ``. Build the match expression in code from sanitized user words. Caveat (source docs): `wrangler d1 export` cannot export a database with virtual tables, so use Time Travel or an app-level export for backups.

Auth tables: generated into `server/db/auth-schema.ts` by `npm run auth:schema`, then included in a normal Drizzle migration. They live in the **same** D1 database as app tables.

## 6. Data access pattern

Core defines the interface; adapters implement it with Drizzle.

```ts
// server/core/items.ts (no drizzle imports)
export interface ItemsRepository {
  get(id: string): Promise<Item | null>;
  insert(item: Item): Promise<void>;
  updateIfRevision(id: string, expected: number, changes: Partial<Item>, meta: { now: Date; userId: string }): Promise<boolean>;
}

// server/adapters/items-repo.ts
import { and, eq, isNull } from "drizzle-orm";
import { items } from "../db/app-schema";
import { atomic, changesOf } from "./atomic";

export function createItemsRepository(db: Database): ItemsRepository {
  return {
    async get(id) {
      const [row] = await db.select().from(items).where(and(eq(items.id, id), isNull(items.deletedAt))).limit(1);
      return row ?? null;
    },
    async insert(item) {
      await atomic(db, [() => db.insert(items).values(item)]);
    },
    async updateIfRevision(id, expected, changes, meta) {
      const [result] = await atomic(db, [
        () => db.update(items)
          .set({ ...changes, revision: expected + 1, updatedAt: meta.now, updatedBy: meta.userId })
          .where(and(eq(items.id, id), eq(items.revision, expected))),
      ]);
      return changesOf(result) === 1;
    },
  };
}
```

Validation happens in core (zod or hand-written), before the repository is called.

## 8. File storage (optional R2)

```ts
// server/adapters/media.ts
export interface MediaStore {
  put(key: string, body: ArrayBuffer | Uint8Array, contentType: string): Promise<void>;
  get(key: string): Promise<{ body: ReadableStream; contentType: string; size: number } | null>;
  delete(key: string): Promise<void>;
  ping(): Promise<void>; // for /health
}
```

- R2 implementation: `bucket.put(key, body, { httpMetadata: { contentType } })`, `bucket.get`, `bucket.delete`, `bucket.list({ limit: 1 })` for ping. No access keys: the binding is the credential.
- Filesystem implementation for Node/tests, with path-traversal checks.
- Files are served through the Worker at `/media/*` (not a public bucket URL), so access rules apply. Public files: `Cache-Control: public, max-age=31536000, immutable`; private: `private, no-store`, and 404 for non-admins.
- Image resizing/re-encoding happens in the browser before upload (CPU limit).

## 10. Provisioning separate resources (do not run while reading; run in the new project)

Prerequisites: a Cloudflare account, and `<APP_DOMAIN>`'s parent zone in that account if you use a custom domain.

```bash
npx wrangler login
```

```bash
npx wrangler d1 create <D1_DATABASE_NAME>
```

Copy the printed `database_id` into `wrangler.jsonc` as `<D1_DATABASE_ID>`.

```bash
npx wrangler r2 bucket create <R2_BUCKET_NAME>
```

(Only if you use R2. R2 may require a payment method on file before it can be enabled.)

Set secrets on the **new** Worker (each prompts for a value):

```bash
npx wrangler secret put BETTER_AUTH_SECRET --name <WORKER_NAME>
```

Repeat for `ADMIN_EMAILS`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `ANTHROPIC_API_KEY`. Generate the auth secret with `openssl rand -base64 32`. List names only with `npx wrangler secret list --name <WORKER_NAME>`.

Apply migrations to the new remote database:

```bash
npx wrangler d1 migrations apply <D1_DATABASE_NAME> --remote -c hosting/cloudflare/wrangler.jsonc
```

Create a **new** Google OAuth client (type Web application) with origin `https://<APP_DOMAIN>` and redirect URI `https://<APP_DOMAIN>/api/auth/callback/google`; for local dev also `http://localhost:5173` and `http://localhost:5173/api/auth/callback/google`.

Create a **new** Anthropic API key for this app.

Always pass `--name <WORKER_NAME>` or `-c hosting/cloudflare/wrangler.jsonc` to Wrangler so commands cannot hit another Worker in the same account (the source guide warns about this).
